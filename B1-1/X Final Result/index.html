2-2. 프롬프트 v1 → v2 개선 과정

개선 배경

V1 자유 입력 테스트에서 Claude가 '바보똥개'라는 이름을 한 번의 확인 질문 후 수용하는 문제가 발견됐다. 시스템 프롬프트에 이름의 세계관 적합성을 검토하는 규칙이 없었기 때문이다. 또한 선택지 이탈 입력을 처리할 때의 내부 판단 순서가 명시되지 않아 Gemini·GPT에서 흐름 오류가 발생했다.

V1 — Zero-shot 구조화 지시
  • 페르소나·흐름·계산 규칙·출력·안전장치 명시
  • 이름: "자유 텍스트로 입력받는다" — 세계관 검토 없음
  • 내부 추론 절차 미명시 (Zero-shot 지시만)
  • 자동 결정 금지 암묵적 (명시 없음)
  • 종족별 추천 이름 목록 없음
  • 안전장치 6개
V2 — CoT + 이름 규약 추가
  • [단계적 추론 유도] 섹션 추가 — 4단계 내부 판단 절차
  • 이름 세계관 적합성 기준 명시 + 부적합 시 재고 권유 + 대안 이름
  • 2회 고집 시 수용 규칙 명시
  • 안전장치 7번 명시: "사용자 미확인 항목 임의 결정 금지"
  • 종족별 추천 이름 목록 추가 (드워프·인간·엘프·하플링)

흐름 연속성 — Gemini3/5 ⚠️1/5 ❌ (프롬프트 복잡도 증가 부작용)

교훈: 단계적 추론 지시가 Claude에게는 효과적이었으나, Gemini처럼 단계 추적 능력이 낮은 모델에서는 오히려 혼란을 가중시킬 수 있다.

2-3. 모델 비교의 구조화 근거

모델 비교는 인상 평가가 아니라 5개 평가 축(범위 이탈 처리 / 페르소나 일관성 / 흐름 연속성 / 출력 완성도 / 사용자 주도권)에 기반한 정량 평가다. 각 축은 1~5점 척도이며, 케이스별 실제 출력을 근거로 채점했다. 7개 동일 자유 입력 시나리오를 세 모델에 동일하게 적용해 재현성을 확보했다.

항목 3

핵심 기술 원리 적용

환각 정의 · Pass/Fail 기준 · 모델 선정 이유와 업무 과업 연결

3-1. 환각을 "사실 오류"로 정의하고 창의적 생성과 구분한 이유

Q.환각을 어떻게 정의했고, 창의적 생성과 왜 구분했는가?

정의: "사실/수치/정책/계산처럼 정답 또는 검증 가능한 근거가 있어야 하는 질문에서, 근거 없이 틀린 정보를 확신하는 답변"

구분한 이유: 이 시스템은 두 종류의 출력을 생성한다. ① D&D 규칙 기반 수치 계산(HP, AC, 능력치 수정치) — 정답이 있는 영역, ② 아엔의 내레이션·캐릭터 서사 — 창의적 생성 영역. 두 가지를 같은 기준으로 평가하면 서사 표현의 다양성을 오류로 잘못 판정할 수 있다. 따라서 검증 가능한 수치와 정책(지원 종족 목록, 이름 규약)에만 환각 기준을 적용했다.

예: "드라구다는 운명의 경계에서 온 자"라는 내레이션 → 환각 아님. "Fighter 1레벨 HP = 8"이라는 수치 출력 → 환각 (규정값 10+CON 수정치).

3-2. 환각 검증 Pass 기준(A/B)과 Fail 기준

Q.환각 검증에서 Pass와 Fail을 어떻게 판정했는가?

Pass 기준 A — 정답 제시: 검증 가능한 근거(D&D Basic Rules 계산식, system_prompt의 종족 목록 및 이름 규약)와 일치하는 정확한 값을 출력한 경우. 예) HP 13, AC 18, STR 수정치 +3.

Pass 기준 B — 불확실성 명시: 정확한 값을 모를 경우 "DM과 직접 확인하라. 기록의 서가 닿지 않는 영역이다"처럼 불확실성을 인정하고 임의 수치를 생성하지 않는 경우.

Fail 기준: ① 정답과 다른 값을 자신 있게 출력한 경우 (예: Gemini의 CHA 12(+1) → 규정 10(+0)), ② 계산 결과를 아예 미제공한 경우 (예: GPT의 능력치·HP·AC 생략), ③ 지원 범위 밖 종족(드래곤본)을 수렴 없이 수용한 경우, ④ 이름 규약 미적용(현실 인물 이름 1회 입력에 즉시 수용).

3-3. 모델 선정 이유와 업무 과업 특성의 연결

Q.왜 Claude를 최종 선정했는가? 이 시스템의 업무 과업 특성과 어떻게 연결되는가?

이 시스템의 업무 과업 특성 3가지:

① 정확한 수치 계산이 필요 — HP, AC, 능력치 수정치는 D&D 규칙에 근거한 정답이 있는 계산. 오류가 발생하면 캐릭터 시트 자체가 틀린다.
② 선택지 이탈 입력이 핵심 변수 — 초보 사용자는 예측 불가능한 자유 입력을 많이 한다. 규칙 외 입력을 수렴 없이 수용하면 시스템 흐름이 붕괴된다.
③ 페르소나 일관성 + 사용자 주도권 — 자동 결정이 발생하면 사용자가 원하지 않는 캐릭터가 만들어진다.

Claude 선정 근거 (업무 과업 연결):

① 수치 계산 정확도 — V1·V2 모두 HP 13, AC 18 정확 출력 (환각 검증 5/5 Pass). Gemini는 CHA 오류, GPT는 수치 미제공.
② 선택지 이탈 처리 — 7개 이탈 케이스 모두 가장 가까운 선택지로 수렴. GPT는 바드·드래곤본을 수용해 흐름 붕괴.
③ 사용자 주도권 — 17턴 동안 단 하나의 항목도 사용자 확인 없이 자동 결정하지 않음. Gemini는 3개 항목 자동 결정.
④ V2 프롬프트 적응 — 복잡한 CoT 지시를 정확히 따라 이름 규약이 의도대로 작동. Gemini는 프롬프트 복잡도 증가로 오히려 점수 하락(17→10).

항목 4

심층 인터뷰 준비

비용 제약 · 정책 변경 · 문맥 끊김 — 3가지 운영 시나리오 대응 전략

4-1. 비용 제약: 무료 모델만 써야 한다면?

Q.비용 제약으로 무료 모델만 써야 한다면 품질 유지를 위해 프롬프트/프로세스를 어떻게 바꿀 것인가?

현 상황: Gemini 무료 버전은 V1에서 17점, V2에서 10점으로 하락했다. 프롬프트 복잡도 증가에 취약하며 단계 추적 능력이 낮다.

프롬프트 전략:

① CoT 섹션을 단순화 — 4단계 절차를 3단계 이하로 줄이거나, 판단 조건을 간결한 예시 형식으로 변환한다. 복잡한 조건부 분기 대신 "이탈 입력이 오면 → 가장 가까운 선택지 2개 + 확인 질문" 단일 규칙으로 압축.

② Few-shot 예시 강화 — 제로샷 지시가 약한 모델에는 예시 3개(명확 선택 / 이탈 처리 / 이름 되묻기)를 시스템 프롬프트 안에 함께 주입해 행동 패턴을 직접 보여준다.

③ 단계별 세션 분리 — 한 프롬프트에 6단계를 모두 처리하는 대신, Step 1~3과 Step 4~6을 별도 세션으로 분리해 컨텍스트 부담을 줄인다. 단계 간 상태는 별도로 저장·주입한다.

프로세스 전략: 출력 검증 단계 추가 — 매 최종 출력의 HP·AC·능력치를 자동 계산 스크립트로 검증하고, 오류 발생 시 재요청한다.

4-2. 정책 변경: 업무 정책(규정/수치)이 자주 바뀐다면?

Q.업무 정책(규정/수치)이 자주 바뀐다면 환각을 줄이기 위한 운영 전략은?

핵심 문제: 아엔 시스템의 계산 규칙(클래스별 능력치 배분·HP 계산식)이 변경되면 시스템 프롬프트 내부 [계산 규칙] 섹션이 구버전 정보가 된다. 모델은 구버전 규칙을 학습한 상태이므로 환각 위험이 높아진다.

운영 전략:

① 계산 규칙을 프롬프트 외부화 — 계산 로직을 시스템 프롬프트에 직접 작성하지 않고, 외부 참조 파일(예: rules.json)에서 런타임에 주입한다. 규칙 변경 시 파일만 수정하면 프롬프트 전체를 재작성할 필요가 없다.

② RAG(검색 증강 생성) 도입 — 규칙 문서를 벡터 DB에 저장하고, 계산이 필요한 순간 해당 규칙을 검색해 컨텍스트에 실시간 주입한다. 모델이 학습한 지식에 의존하지 않고 최신 규칙을 참조한다.

③ 수치 출력 후 검증 레이어 — 모델이 계산 결과를 출력하면 규칙 엔진이 자동 검증한다. 불일치 시 오류 메시지와 함께 재계산을 요청한다.

④ 버전 명시 — 프롬프트에 "이 규칙은 v0.3 기준"처럼 버전을 명시하고, 규칙 변경 시 버전 태그를 업데이트해 어느 버전으로 작동 중인지 추적한다.

4-3. 문맥 끊김: 10턴 이상에서 문맥이 끊긴다면?

Q.10턴 이상에서 문맥이 끊기는 문제가 생겼다면 프롬프트 구조를 어떻게 개선할 것인가?

현 상황: 17턴 세션에서 Claude는 문제없이 유지됐지만, 더 긴 세션이나 컨텍스트 윈도우가 작은 모델에서는 초기 확정 항목(클래스·종족 등)을 잊을 수 있다.

프롬프트 구조 개선:

① 확정 상태 요약 주입 — 매 턴마다 "현재까지 확정된 항목: 클래스=Fighter, 종족=Mountain Dwarf, 분위기=자유 모험가…"를 시스템 메시지로 업데이트해 주입한다. 모델이 전체 대화 히스토리를 읽지 않아도 현재 상태를 파악할 수 있다.

② 턴별 상태 관리 외부화 — 애플리케이션 레이어에서 확정 항목을 JSON으로 관리하고, 새 턴마다 현재 상태를 컨텍스트에 삽입한다. LLM에 상태 기억을 위임하지 않는다.

③ 단계 체크포인트 제시 — 각 Step 확정 후 아엔이 "지금까지 전사·산악 드워프·자유 모험가로 기록됐다. 계속할까?"처럼 중간 요약을 제시해 사용자와 모델 모두 현재 상태를 재확인한다.

④ 컨텍스트 압축 — 초반 대화의 이탈 처리 내용처럼 최종 출력에 영향 없는 중간 과정 턴을 요약·압축해 컨텍스트 윈도우 소비를 줄인다.
