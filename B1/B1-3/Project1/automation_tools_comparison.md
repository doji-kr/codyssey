# 자동화 툴 비교 — n8n · Make · Zapier

> Codyssey · AI Native — No-Code Automation 비교 데이터시트
> 같은 일을 하는 세 도구. 하지만 "어떻게" 하느냐에서 설계 철학이 갈린다.

## 도구별 정체성

| 도구 | 성격 | 한 줄 요약 |
|---|---|---|
| **Zapier** | Breadth · Ease-first | 폭과 속도를 위해 깊이·비용효율을 판다. 8,000+ 앱을 가장 빠르게 연결. |
| **Make** | Visual · Mid-tier | 시각적 명료성을 위해 약간의 복잡도를 산다. 데이터 흐름이 눈에 보인다. |
| **n8n** | Control · Code-native | 통제·확장성을 위해 진입 비용을 떠안는다. self-host + 코드 노드 + AI 네이티브. |

## 01. 9개 축 비교 매트릭스

> ★ = 해당 축 우위

| 비교 항목 | Zapier | Make | n8n |
|---|---|---|---|
| **UI / UX** | ★ 선형 단계형 빌더. 가장 깔끔·직관적 | 캔버스형 플로우차트, 가장 시각적 | 노드 그래프, 강력하나 기술적 |
| **설정 난이도** | ★ 가장 낮음. 30분 미만, 인프라 셋업 없음 | 중간. router·iterator에서 가팔라짐 | 가장 높음. self-host는 서버·Docker 필요 |
| **연동 서비스 범위** | ★ 8,000+ 압도적 1위 | ~3,000 중간 규모 | ~1,100 최소, 단 HTTP/코드로 무엇이든 |
| **무료 플랜 범위** | 월 100 task, 2-스텝 한정 | 월 1,000 ops, 시나리오 2개 | ★ self-host 시 실행 무제한·무료 |
| **실행 로그 확인** | Zap History, task 단위 | History 탭, 모듈별 데이터 시각 열람 | ★ Executions 탭, 노드별 입출력·재실행, 로그 직접 통제 |
| **과금 단위** | 액션마다 task — 복잡도가 곧 비용 | 모듈마다 operation, 폴링이 쿼터 소진 | ★ 워크플로 1회=1 execution, 스텝 수 무관 |
| **데이터 주권 / 호스팅** | 완전 호스팅(SaaS) | 완전 호스팅(SaaS) | ★ 오픈소스 self-host, 데이터 직접 통제 |
| **제어 흐름** | 선형, 복잡 분기에 약함 | ★ 비주얼 분기 + iterator | ★ 노드 그래프 + JS/Python 코드 |
| **AI 에이전트** | Agents·Copilot, AI를 API로 취급 | Make AI Agents, reasoning 패널 | ★ 네이티브 LangChain·70+ 노드·영속 메모리·로컬 LLM |

## 02. 각 도구의 장단점

### Zapier — The Connector
**장점**
- 업계 최대 통합 라이브러리(8,000+) — 거의 모든 SaaS 커버
- 가장 낮은 진입 장벽, 가장 빠른 time-to-value
- 가장 깔끔한 UI, 인프라·유지보수 부담 없음

**단점**
- 스케일에서 가장 비쌈 — task 과금이 복잡도를 처벌
- 선형 구조라 복잡한 분기·반복에 취약
- 깊은 커스터마이징·코드 제어가 제한적

### Make — The Visual Builder
**장점**
- 세 도구 중 디버깅 가시성 최고 — 데이터 흐름이 보임
- 가성비 좋은 중간 티어 + 후한 무료(1,000 ops)
- router·iterator로 강력한 분기·배치 처리

**단점**
- operation 과금 — 매분 폴링이면 월 ~43,000 ops 선소진
- Zapier보다 적은 통합(~3,000)
- self-host 불가, router 도입 시 곡선 가팔라짐

### n8n — The Engine
**장점**
- 스케일에서 가장 저렴 — execution 과금, self-host는 무제한 무료
- self-host = 완전한 데이터 주권
- JS/Python 코드 노드 — 가장 깊은 커스터마이징
- AI 네이티브(LangChain·에이전트·로컬 LLM)

**단점**
- 가장 가파른 학습 곡선
- 사전 통합 가장 적음 — HTTP 노드 의존
- self-host 시 인프라·DevOps 책임을 직접 부담

### 스케일 비용 (8-스텝 × 10,000회/월 동일 작업)

| Zapier | Make | n8n Cloud |
|---|---|---|
| $250~400+ /월 (80,000 task) | $150~200 /월 (80,000 ops) | $50 /월 (10,000 exec) |

> 복잡할수록 격차가 벌어진다. self-host n8n은 서버비만 든다.

## 03. 어떤 상황에 적합한가 — 평가 의견

- **Zapier 선택** — 비기술 팀이 빠르게 붙여야 할 때. 단순·직관적 워크플로, 크지 않은 볼륨, 비용보다 속도·편의 우선.
- **Make 선택** — 시각적 사고형 + 중간 복잡도. 분기는 필요하나 self-host 부담은 싫고, Zapier보다 저렴한 가성비를 원할 때.
- **n8n 선택** — 기술 리소스 보유 + 통제 필요. 대용량·복잡 파이프라인, 데이터 프라이버시 최우선, AI 에이전트/로컬 LLM, self-host 환경.

### 종합 의견
시장 일반론으로는 "상황별 정답이 다르다"가 맞다. 셋의 차이는 우열이 아니라 **최적화 대상의 선택**이다 — Zapier는 폭, Make는 시각적 명료성, n8n은 통제. 각자가 무언가를 얻기 위해 무언가를 포기했다.

다만 평가의 가중치는 사용자에 따라 뒤집힌다. n8n의 최대 약점인 "설정 난이도"와 "통합 부족"은, 시스템 프로그래밍 배경 + 이미 self-host 인프라(NAS·Docker)를 운영 중인 사용자에게는 거의 무력화된다. 코드 노드는 마찰이 아니라 자유가 되고, HTTP 노드는 한계가 아니라 만능이 된다.

그래서 동일 워크플로를 Make와 n8n 양쪽에 구현해 보는 것은 단순 반복이 아니라, operation 모델과 execution 모델이 같은 로직을 어떻게 다르게 과금·실행하는지를 체득하는 과정이다. 점수분류 같은 단순 분기에서는 차이가 작아 보이지만, 멀티스텝 파이프라인으로 갈수록 이 과금 단위 하나가 도구 선택을 결정짓는다.
