01

INPUT travel_planner.py

argparse로 --date를 받아 validate_date()가 형식(YYYY-MM-DD)과 범위(내일 이후 ~ 1년 이내)를 검증한다. 실패하면 ArgumentTypeError를 던져 argparse가 usage를 출력하고 종료 코드 2로 종료한다.

02

CACHE _load_cache()

같은 날짜의 {date}_raw_data.json과 {date}_travel_plan.md가 이미 있으면 외부 API 호출을 전부 건너뛰고 즉시 반환한다. 심화 과제로 요구된 멱등성(idempotency) 로직.

03

WEATHER weather.py

후보 도시 11곳 각각에 대해 Open-Meteo Climate API를 호출한다. 대상 날짜의 (월·일) 기준 ±3일 구간을 2000년 기후 모델(MRI_AGCM3_2_S)로 조회해 평균기온·습도 평년값을 얻는다 — 미래 날짜라도 실측 기반 값을 쓰기 위한 설계.

04

SCORE _comfort_score()

기온 18~24°C·습도 40~60%에 가까울수록 높은 점수를 주는 결정론적 함수로 11개 도시를 채점하고 최고점 도시를 선정한다. LLM이 아니라 순수 Python 계산이라 같은 입력이면 항상 같은 결과가 나온다(재현 가능).

05

FESTIVAL tour.py: fetch_festivals()

확정된 area_code로 TourAPI searchFestival2를 호출해 당월 축제를 받고, 대상 날짜가 eventstartdate~eventenddate 사이에 포함되는 것만 필터링한다. 0건이어도 빈 배열로 정상 진행.

06

STAY tour.py: fetch_stays()

같은 area_code로 TourAPI searchStay2를 호출한다. 축제 조회와 동일한 _call_tour_api() 범용 함수를 재사용해 엔드포인트 이름만 바꿔 한 줄로 추가한 심화 과제 구현.

07

RESTAURANT places.py: fetch_restaurants()

Kakao Local 키워드 검색에 "{도시명} 맛집"과 category_group_code=FD6(음식점)을 함께 보내 10곳을 받는다. 401/403은 AUTH_ERROR로 기록 후 빈 배열 반환.

08

IMAGE places.py: fetch_city_images() / _fetch_one_image()

Kakao Image Search로 도시 대표 이미지 6장과, 맛집별 이미지를 ThreadPoolExecutor(max_workers=5)로 병렬 조회한다. 이 단계에서 4개 API 순회(Fan-out)가 마무리된다.

09

AGGREGATE travel_planner.py: run()

지금까지 모은 city·festivals·restaurants·stays·errors를 하나의 raw_data 딕셔너리로 합친다. 이 시점부터 LLM 프롬프트의 입력이 확정된다.

10

LLM REPORT llm.py: generate_report()

OpenRouter(google/gemini-2.5-flash)에 raw_data 전체를 JSON 텍스트로 박아넣고 "데이터에 없는 정보는 지어내지 말 것"을 명시한 프롬프트로 마크다운 리포트를 생성한다.

11

RETRY llm.py: _call_llm() / _fallback_report()

LLM 호출이 실패하면 "반드시 순수한 마크다운만 반환하라"는 문구를 덧붙여 1회 재시도한다. 그래도 실패하면 _fallback_report()가 최소한의 마크다운 뼈대를 대신 만든다.

12

SAVE report.py: save()

results/ 폴더를 생성(이미 있으면 재사용)하고 {date}_raw_data.json과 {date}_travel_plan.md를 저장한다. 이 두 파일이 다음 실행의 캐시(2단계)로 재사용된다.

2
Study — 학습 목표

이 과제를 마친 후
스스로 설명할 수 있어야 하는 것

아래 네 가지는 과제 가이드가 요구하는 핵심 역량이다. 각 항목마다 이 프로젝트에서 실제로 어떤 코드가 그 개념을 구현했는지를 근거로 든다.

① REST API 요청/응답 구조와 GET/POST의 차이

이 프로젝트가 호출하는 4개의 외부 API는 전부 GET이고, 유일하게 OpenRouter LLM 호출만 POST다. 이유는 단순한 규칙이 아니라 각 호출의 성격에서 나온다 — 조회(읽기, 멱등)는 GET, 생성(부수효과, 비멱등)은 POST.

API메서드인증 방식이유

TourAPI (축제·숙박)GETQuery serviceKey지역코드 기준 목록 조회. 같은 요청을 반복해도 결과 동일(멱등)

흥미로운 사례: 이 프로젝트의 웹 서버(server.py)는 파이프라인을 "실행"시키는 /api/plan도 GET으로 만들었다. 일반적으로 실행/생성 트리거는 POST가 어울리지만, 브라우저의 EventSource(SSE 수신 API)는 GET 요청만 지원하기 때문에 실시간 로그 스트리밍이라는 요구사항이 메서드 선택을 결정했다. REST 원칙과 실제 브라우저 API 제약이 충돌할 때 어떤 판단을 하는지 보여주는 예시.

② LLM 출력의 구조화(JSON)와 파이프라인 연동

과제 원안은 "1차 LLM 호출이 {recommended_city, weather, events, reason} JSON을 생성하고, 이를 2차 지도 API 입력으로 쓴다"는 흐름이다. 이 프로젝트는 이 구조를 의도적으로 바꿨다 — 도시 선정을 LLM이 아니라 Open-Meteo 실측 데이터 기반 결정론적 점수 계산(weather.py: select_best_city())으로 대체했다.

weather.py — LLM 대신 결정론적 로직이 만드는 구조화 JSON 
# select_best_city()가 반환하는 구조 — 원래 스펙의 1차 JSON과 같은 "역할"을 한다
{
  "recommended_city": "속초",
  "area_code": 32,
  "weather": {"avg_temp_c": 24.2, "humidity_pct": 80.4, "source": "open-meteo-climate"},
  "score": 0.568
}
# ↓ 이 JSON의 area_code는 TourAPI 호출 파라미터로,
#   recommended_city는 Kakao Local 검색어로 그대로 흘러들어간다

왜 바꿨는가? 프로젝트 CLAUDE.md에 명시된 설계 철학 때문이다 — "LLM은 데이터를 지어내지 않는다." LLM에게 "7월에 강릉 날씨가 어떤지" 물으면 그럴듯하지만 검증 불가능한 문장을 만들어낼 수 있다. 반면 Open-Meteo는 실제 기후 관측값을 준다. 그래서 이 프로젝트는 구조화 데이터 핸드오프라는 학습 목표는 그대로 유지하면서, 그 구조화 데이터를 만드는 주체만 "LLM"에서 "결정론적 Python 코드"로 옮겼다.

대신 LLM은 파이프라인의 마지막 단계에서 정반대 방향의 변환을 담당한다 — 날씨·축제·맛집·숙박이라는 구조화된 JSON 전체를 입력으로 받아, 사람이 읽는 비구조화 마크다운 텍스트로 바꾼다(llm.py: generate_report()). 구조화 입력→출력과 비구조화 입력→출력을 한 파이프라인 안에서 모두 경험하는 구조다.

③ 외부 API 오류(인증/쿼터/네트워크/파싱)와 대응 원칙

각 모듈은 실패 유형별로 다른 처리를 한다. 핵심 원칙은 하나 — 부분 실패가 전체 파이프라인을 죽이지 않는다. 실패는 예외를 삼키고 errors[] 리스트에 기록한 뒤 빈 결과로 다음 단계를 계속 진행한다.

④ API 키를 .env로 관리하는 이유

이유를 교과서적으로 설명하면 "하드코딩하면 Git에 올라가서 유출된다"이다. 이 프로젝트를 개발하던 중 그 위험이 이론이 아니라는 걸 실제로 확인한 사건이 있었다 — 자세한 내용은 4장 보안 자체 점검에 정리했다. 요약하면: 같은 저장소의 다른 프로젝트 문서(예시 코드)에 실제 키와 같은 접두사를 가진 문자열이 커밋되어 GitHub에 이미 푸시되어 있었고, 이를 git filter-repo로 히스토리에서 제거하고 강제 푸시해야 했다. "예시로만 써도 진짜 키와 헷갈릴 만한 문자열은 절대 커밋하면 안 된다"는 교훈을 이 프로젝트가 직접 얻었다.

실제 사례: 키 노출 의심 → 대응 → 오탐(false positive) 확인

이 프로젝트를 Docker로 빌드·배포하는 과정에서 실제 OpenRouter 키를 .env에 넣어 테스트했다. 이후 같은 Git 저장소의 다른 프로젝트 문서(보안 교육용 예시 코드가 담긴 explainer 페이지)를 점검하던 중, 방금 사용한 키와 동일한 접두사 문자열이 이미 커밋되어 GitHub에 푸시된 상태임을 발견했다.

1단계 — 발견: git log --all -S "<key-prefix>"로 히스토리 전체를 검색해, 예시 코드("이렇게 하면 안 됩니다")로 작성된 문서에 실제 키와 같은 접두사가 남아있고 이미 원격에 푸시되었음을 확인.
2단계 — 즉시 대응: 사용자에게 즉시 보고하고, (a) 키 폐기, (b) 예시 문자열만 수정, (c) 예시 문자열 수정 + Git 히스토리에서 완전 제거 중 선택지를 물었다. 사용자는 (c)를 선택 → git filter-repo --replace-text로 전체 히스토리에서 문자열을 치환하고 git push --force로 원격 저장소를 갱신했다.
3단계 — 최종 확인: 이후 사용자가 해당 문자열이 실제로는 예시용 가짜 키였음을 확인해줬다 — 즉 이번 건은 오탐(false positive)이었다. 다만 판별 이전 단계에서 잠재적 유출로 간주하고 즉시 조치한 판단 자체는 유지한다: 실제 키인지 예시 키인지 텍스트만으로 100% 확신할 수 없는 상황에서는, 확인 전까지 "유출로 간주하고 대응"하는 것이 안전한 기본값이다.
실행한 대응 명령 요약 
# 1. 노출 의심 문자열이 히스토리 어느 커밋에 있는지 특정
git log --all -S "<key-prefix>" --source --oneline

# 2. 해당 문자열을 전체 히스토리에서 치환 (replacements.txt: old==>new)
git filter-repo --replace-text replacements.txt --force

# 3. 치환 후 히스토리에 남아있지 않은지 재검증
git rev-list --all | xargs -I{} git grep -l "<key-prefix>" {}

# 4. 원격 갱신 (filter-repo가 안전장치로 제거한 origin 재등록 후 강제 푸시)
git remote add origin <repo-url>
git push --force origin main

교훈

이 사례는 "학습 목표 ④ API 키를 .env로 관리하는 이유"를 이론이 아니라 실제로 겪은 문제로 만들어줬다. 두 가지를 배웠다:

🚫

예시 코드도 예외 없음

"이렇게 하면 안 됩니다"라는 교육용 예시라도, 실제 키와 헷갈릴 수 있는 문자열(같은 접두사, 같은 길이감)은 커밋하지 않는다. 완전한 더미 값(sk-or-v1-xxxxxxxx)만 사용한다.

🔍

의심되면 즉시 폐기가 기본값

노출 여부가 불확실할 때 "확실해질 때까지 기다리기"보다 "일단 폐기하고 재발급"이 비용이 훨씬 싸다. API 키 재발급은 몇 초, 무단 사용으로 인한 과금은 되돌릴 수 없다.

Usage — 실행 방법

Docker든 로컬이든
날짜 하나로 쿼리를 던지는 4가지 방법

실행 환경(Docker / 로컬)과 인터페이스(웹 API / CLI)를 조합하면 4가지 실행 경로가 나온다. 어떤 경로를 쓰든 파이프라인 코드(travel_planner.py: run())는 동일하게 동작한다 — 차이는 "누가 --date를 넘겨주느냐"뿐이다.

상황명령
Docker 컨테이너에 날짜 쿼리 (웹 API)curl -N "http://localhost:8000/api/plan?date=2026-07-15"
Docker 컨테이너 내부에서 CLI 직접 실행docker exec -it travel-agent python travel_planner.py --date "2026-07-15"
Docker 없이 로컬에서 CLI 직접 실행python travel_planner.py --date "2026-07-15"
Docker 없이 로컬 웹서버 실행 후 쿼리python server.py 후 동일한 curl
Docker 컨테이너에 명령 내리기

컨테이너가 이미 docker compose up -d로 떠 있다고 가정한다.

방법 A — 웹 API로 날짜 쿼리 (curl) 
# /api/plan은 SSE(Server-Sent Events)로 응답 → -N(no-buffer) 필수
curl -N "http://localhost:8000/api/plan?date=2026-07-15"
방법 B — 컨테이너 내부에서 CLI 스크립트 직접 실행 
# docker compose로 띄운 경우 (서비스명 = travel-agent)
docker compose exec travel-agent python travel_planner.py --date "2026-07-15"

# docker run --name travel-agent 로 띄운 경우
docker exec -it travel-agent python travel_planner.py --date "2026-07-15"

# 컨테이너 이름/서비스명이 다르면 확인
docker ps
웹 서버 없이 CLI를 컨테이너 안에서 직접 실행해도 results/는 볼륨 마운트(./results:/app/results)돼 있어 호스트에서 즉시 결과 파일을 확인할 수 있다.
Docker 없이 실행 (일반 Python 프로그램)

호스트에 가상환경을 만들어 travel_planner.py나 server.py를 직접 돌리는 방식. Docker 데몬이 없어도 동일한 파이프라인을 실행할 수 있다.

1) 가상환경 준비 (최초 1회) 
python3 -m venv .venv
source .venv/bin/activate    # Windows: .venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env         # .env에 API 키 3개 입력
2-A) CLI로 직접 실행 — 리포트만 생성하고 종료 
python travel_planner.py --date "2026-07-15"

# 잘못된 형식/범위는 usage 출력 후 종료 코드 2로 종료
python travel_planner.py --date "2026-13-99"   # 형식 오류
python travel_planner.py --date "2026-01-01"   # 오늘 이전 날짜
2-B) 웹서버로 실행 — 브라우저 또는 curl로 쿼리 
.venv/bin/python server.py
# → http://localhost:8000 접속, 또는 동일한 curl 명령 사용 가능
curl -N "http://localhost:8000/api/plan?date=2026-07-15"
날짜 쿼리 예시 — 정상/오류 응답 비교
# 정상 — 오늘 이후 ~ 1년 이내
curl -i "http://localhost:8000/api/plan?date=2026-07-15"

# 형식 오류(월 13, 일 99) → HTTP 400
curl -i "http://localhost:8000/api/plan?date=2026-13-99"
# {"detail":"올바르지 않은 날짜 형식: '2026-13-99'. YYYY-MM-DD 형식을 사용하세요."}

# 과거 날짜 → HTTP 400
curl -i "http://localhost:8000/api/plan?date=2026-01-01"
# {"detail":"'2026-01-01'은 오늘 이전 날짜입니다. 내일 이후 날짜를 입력하세요."}

검증 로직은 CLI(validate_date())와 서버(check_date()) 양쪽에 동일한 규칙(형식 · 오늘 이후 · 1년 이내)으로 구현돼 있다 — 실행 경로와 무관하게 같은 날짜는 항상 같은 검증 결과를 낸다. 자세한 옵션은 README "실행 방법 한눈에 보기" 절 참고.
