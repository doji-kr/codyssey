트리거

01
iHeartDogs RSS
n8n-nodes-base.rssFeedRead · v1.2
소스

RSS 피드를 읽어 최신 글들을 각각 하나의 아이템으로 변환하는 소스 노드. 이후 모든 노드는 여기서 나온 아이템 묶음을 순서대로 받아 처리한다.

입력 트리거출력 글 아이템 ×N
RSS가 어떻게 동작하나

RSS 피드는 사이트가 발행하는 XML 문서다. 문서 안에는 <channel>이 있고 그 안에 글 하나당 <item> 요소가 들어간다. 각 item은 <title> <link> <description> <guid> <pubDate> 같은 태그를 갖는다. rssFeedRead 노드는 이 XML을 받아 파싱해서 태그를 JSON 키로 바꾼다 — <description>은 contentSnippet, <pubDate>는 표준화된 isoDate로 변환되는 식이다. 즉 "JSON 리턴"은 피드가 JSON을 주는 게 아니라, 노드가 XML을 읽어 JSON 아이템으로 옮긴 결과다.

반환 개수 규칙

개수는 노드가 아니라 발행하는 사이트가 정한다. 피드 XML에는 "가장 최근 N개"만 담기는 롤링 윈도우 방식이라, 새 글이 올라오면 가장 오래된 글이 피드에서 밀려난다. iHeartDogs는 WordPress 기반이고, WordPress는 설정 → 읽기 → "구독 피드에 보여줄 최근 항목 수"로 이 값을 정한다(기본 10, 사이트가 더 크게 설정 가능). 그래서 한 번 읽을 때 들어오는 개수는 그 사이트 피드 설정값과 같다. 노드는 그 시점 XML에 담긴 item 전부를 그대로 아이템으로 만든다.

핵심 옵션
옵션값설명
urlhttps://iheartdogs.com/feed읽어올 피드 주소
options{}SSL 무시·커스텀 필드 등 부가 옵션
출력 필드 (다음 노드에서 쓰는 키)
필드의미
title글 제목
contentSnippet본문 텍스트(태그 제거된 요약)
link원문 URL → 최종 레코드의 source_url
guid글 고유 식별자 → 중복 제거 키 (아래 설명)
isoDate발행일시(ISO 8601) → pub_date
guid란 무엇인가

guid(globally unique identifier)는 RSS 규격에서 글 하나를 영구히 식별하는 문자열이다. WordPress는 보통 글의 영구 ID(예: https://iheartdogs.com/?p=12345)를 guid로 쓴다. 규격상 같은 글은 언제 읽어도 같은 guid를 가져야 하므로, 한 글의 guid는 발행 후 바뀌지 않는 불변 값으로 다루면 된다. 글 내용을 수정·재발행해도 guid는 유지된다. guid가 바뀌는 경우는 사실상 사이트가 guid 생성 방식 자체를 바꾸거나(예: 도메인 이전 후 재생성) 글을 삭제 후 새로 올리는 경우뿐이다. 이 불변성 덕분에 다음 단계의 중복 제거가 "같은 글"을 안정적으로 알아본다. guid가 없는 일부 피드를 대비해 이 파이프라인은 guid || link로 보조 키를 둔다.

커스터마이징
  • url만 바꾸면 어떤 피드로도 재사용 가능 — Synthtopia, 특정 블로그 등.
  • 여러 피드를 합치려면 RSS 노드를 복수로 두고 Merge 노드로 모은다.
  • 한 번에 더/덜 받고 싶으면 노드가 아니라 발행 사이트의 피드 항목 수 설정을 봐야 한다(외부 사이트는 조정 불가).
02
Filter Topic
n8n-nodes-base.if · v2.2
로직 · 1차 필터

RSS 노드가 넘긴 각 글에 대해, 제목 + 본문에 반려견 관련 키워드가 하나라도 있는지 정규식으로 검사한다. 조건이 참인 글만 통과시키는 1차 관문이다. IF 노드는 true/false 두 갈래 출력을 갖지만 이 파이프라인은 true 갈래만 이어 필터로 쓴다(거짓 글은 흘려보내지 않고 멈춤).

입력 RSS 아이템true → Select Topicfalse 버림
무엇을, 어떻게 거르나

거르는 대상은 바로 앞 노드(iHeartDogs RSS)가 내보낸 글 아이템들이다. 노드는 들어온 아이템을 하나씩 꺼내, 각 아이템의 $json(그 글의 title·contentSnippet 등)을 조건식에 대입해 평가한다. 여기서 leftValue는 그 자체가 true/false를 돌려주는 정규식 표현식이고, operator.type = boolean / operation = true는 "그 결과가 불리언 true인가"를 판정하는 비교 규칙이다. 결과가 true면 그 아이템을 true 출력으로, 아니면 false 출력으로 보낸다. 즉 거르는 단위는 묶음이 아니라 아이템 하나하나이며, 통과 여부는 각 글에 대해 독립적으로 결정된다.

조건식
// 각 글의 title + contentSnippet 에 키워드 매칭 (대소문자 무시)
/dog|puppy|breed|training|health|vet|nutrition|
 food|adoption|rescue|behavior|safety|recall/i
  .test(($json.title||'') + ' ' + ($json.contentSnippet||''))
핵심 옵션
옵션값설명
operator.typebooleanleftValue를 불리언으로 보고 비교한다는 뜻. 함께 쓰인 operation true는 "값이 true일 때 통과"
operationtruesingleValue 비교 — leftValue가 그대로 true면 참, 아니면 거짓
combinatorand조건이 여러 개일 때 결합 방식(모두 참이어야 통과)
typeValidationstrict아래 설명
typeValidation = strict 의 의미

strict는 타입 자동 변환을 하지 않는 모드다. 비교 대상 값이 기대한 타입(여기선 불리언)과 다르면 n8n이 몰래 형변환해서 어물쩍 넘기지 않고 오류를 낸다. 예를 들어 leftValue가 문자열 "true"나 숫자 1처럼 불리언이 아니면, loose 모드는 적당히 true로 바꿔 통과시키지만 strict는 멈추고 에러를 표시한다. 덕분에 "왜 통과됐지/안 됐지"가 형변환 때문에 흐려지지 않고, 조건이 의도대로 불리언으로만 평가되도록 강제된다. 이 노드의 leftValue는 정규식 .test() 결과라 항상 진짜 불리언이므로 strict와 잘 맞는다.

커스터마이징
  • 정규식의 키워드|키워드 목록만 손보면 관심 주제를 넓히거나 좁힐 수 있다.
  • 버려지는 false 갈래를 따로 연결하면 "탈락 로그 시트" 같은 분기를 추가할 수 있다 — 과제의 "양쪽 경로 실행" 요건을 채우는 방법.

Select Topic
n8n-nodes-base.if · v2.2
로직 · 2차 필터

1차 통과분 중 하나의 세부 토픽만 추가로 골라낸다. 코드 안 TOPIC 상수(현재 'training')가 가리키는 정규식으로 제목·본문을 다시 검사한다. 토픽별 정규식이 MAP에 미리 정의돼 있어 값 하나만 바꾸면 대상 주제가 바뀐다.

입력 Filter Topic(true)true → Remove Duplicatesfalse 버림
토픽 맵
const TOPIC = 'training';   // 이 값만 바꾸면 됨
health    → /health|vet|disease|symptom|illness/i
training  → /training|train|obedience|behavior/i
adoption  → /adoption|adopt|rescue|shelter/i
nutrition → /nutrition|food|diet|feeding|treat/i
safety    → /safety|recall|warning|hazard|danger/i
breed     → /breed|puppy|breeds/i
커스터마이징
  • TOPIC 값을 health · training · adoption · nutrition · safety · breed 중 하나로 교체.
  • MAP에 줄을 추가하면 새 토픽을 만들 수 있다(키 + 정규식).
  • 여러 토픽을 동시에 받으려면 이 노드를 Switch로 바꿔 토픽별 갈래로 분기한다.
04
Remove Duplicates
n8n-nodes-base.removeDuplicates · v2
로직 · 중복 제거

이전 실행에서 이미 처리한 글을 걸러낸다. n8n이 "본 적 있는 키"를 데이터베이스에 기억해 두고, 같은 키가 다시 오면 버린다. 매일 같은 피드를 읽어도 새 글만 LLM·이미지 단계로 넘겨 비용과 중복 적재를 막는 노드.

입력 Select Topic(true)출력 새 글만 → Check DB Duplicate
"본 적 있는 키"는 어디에 · 얼마나 저장되나

이 기억은 워크플로우 실행 데이터가 아니라 n8n 인스턴스 자체의 데이터베이스에 들어간다(기본 설치는 SQLite, 보통은 Postgres). 저장되는 건 글 전체가 아니라 dedupeValue로 평가된 키 문자열(여기선 각 글의 guid)뿐이라 용량 부담이 작다. 이 저장소는 실행과 실행 사이에 계속 유지되며, 그래서 "이전 실행에서 봤는지"를 비교할 수 있다.

저장 범위와 한도는 노드 옵션으로 조정한다. Scope는 기본 Node(이 노드만의 독립 저장)이고 Workflow로 바꾸면 같은 워크플로우의 다른 Remove Duplicates 노드와 기억을 공유한다. History Size는 기억할 키 개수 상한으로 기본 10,000개다. 즉 가장 최근 키 1만 개까지 추적하며, 필요하면 이 값을 키워 더 멀리까지 중복을 막을 수 있다.

핵심 옵션
옵션값설명
operationremoveItemsSeenInPreviousExecutions현재 입력을 DB에 누적된 과거 키와 비교해 중복 제거
dedupeValue{{ $json.guid || $json.link }}중복 판단 기준 키 — guid가 비면 link로 대체
ScopeNode (기본)이 노드 전용 저장 / Workflow는 노드 간 공유
History Size10,000 (기본)추적할 키 개수 상한
기억 초기화 방법

테스트로 같은 글을 다시 흘리고 싶을 때는 저장된 키를 비워야 한다. 이때는 같은 노드를 잠깐 operation = Clear Deduplication History + Mode = Clean Database로 바꿔 한 번 실행하면 그 노드(또는 Scope에 따라 워크플로우)의 키 저장소가 통째로 지워진다. 그 뒤 다시 원래 operation으로 돌리면, 다음 실행은 모든 글을 "새 글"로 보고 처음부터 다시 쌓는다.

커스터마이징
  • 피드의 guid가 불안정하면 dedupeValue를 $json.link 단독이나 제목 해시 등으로 바꾼다.
  • 아주 오래된 글까지 영구히 막아야 하면 History Size를 올린다(저장 키가 늘어나는 만큼 DB도 커진다).
  • "새 글이면 통과"가 아니라 "발행일이 더 최신이면 통과" 같은 기준이 필요하면 Keep Items Where를 날짜/숫자 비교로 바꿀 수 있다.
05
Check DB Duplicate
n8n-nodes-base.httpRequest · v4.4
검증 · DB 조회

AI 처리에 들어가기 전, NocoDB 테이블을 실제로 조회해 같은 글이 이미 적재돼 있는지 확인한다. 앞쪽 Remove Duplicates가 n8n 내부 히스토리를 보는 1차 방어라면, 이 노드는 DB의 실제 데이터를 기준으로 삼는 2차 방어다. link가 일치하는 레코드를 1건만 찾아 그 존재 여부를 다음 노드로 넘긴다.

입력 Remove Duplicates출력 조회 결과(list) → Is New?인증 NocoDB Token
핵심 옵션
옵션값설명
method · urlGET …/tables/{table}/records레코드 목록 조회 엔드포인트(고정 URL, 제출 시 마스킹)
where(source_url,eq,{{ $json.link }})이번 글의 link와 source_url이 같은 레코드만 필터
limit1존재 여부만 보면 되므로 1건이면 충분
$json.link 으로 조회하는 이유

이 위치에서 $json은 바로 앞 Remove Duplicates의 출력(원본 RSS 아이템)이라 거기 link 필드가 그대로 있다. 그래서 별도 노드 참조 없이 $json.link로 곧장 조회한다 — 아직 실행되지 않은 뒤쪽 노드(Parse JSON Backup 등)를 참조하면 안 된다.

왜 두 단계로 중복을 막나

Remove Duplicates(히스토리)는 1차 방어지만, 히스토리와 DB가 어긋난 경우 — 레코드 수동 삭제, 히스토리 초기화, 다른 경로로 삽입 등 — 를 놓칠 수 있다. 이 조회를 AI 처리 앞에 둔 덕분에, 그런 경우의 중복 글도 LLM·이미지 비용을 쓰기 전에 걸러진다. 두 방어가 상호 보완한다.

커스터마이징
  • 매칭을 더 엄격히 하려면 link 대신 guid로 조회하거나 where에 조건을 추가한다.
  • link에 쿼리스트링(?·&·,)이 섞이는 피드라면 where 값 인코딩을 점검한다(iHeartDogs 퍼머링크는 대개 깨끗).
06
Is New?

배칭(batching)이란

이 노드에는 글이 여러 개(통과한 신규 글 N개)가 한꺼번에 들어온다. 배칭을 안 쓰면 n8n은 그 N개에 대한 API 호출을 거의 동시에 쏟아붓는다 — 외부 API의 분당 호출 한도(rate limit)를 순식간에 넘겨 429 오류를 부르기 쉽다. 배칭은 들어온 아이템을 여러 묶음(batch)으로 쪼개 순차 처리하고, 묶음과 묶음 사이에 batchInterval만큼 쉰다. 여기선 5초 간격을 둬서 호출이 시간에 걸쳐 고르게 퍼지도록 한다. 글이 많을수록 이 간격을 늘리면 한도를 안전하게 지킬 수 있다(대신 전체 실행은 느려진다).

재시도(retry)란 · "실패"의 정의

HTTP 요청 노드에서 "실패"는 그 호출이 정상 응답으로 끝나지 못한 상태를 뜻한다 — 구체적으로 4xx·5xx 같은 비정상 상태코드, 연결 타임아웃, 네트워크 끊김, API 측 오류 응답 등이다. retryOnFail이 켜져 있으면 그런 실패가 났을 때 n8n이 그 호출을 바로 포기하지 않고 다시 시도한다. maxTries = 3은 처음 1회 + 재시도를 포함해 최대 3번까지 굴린다는 뜻이고, waitBetweenTries = 3000은 시도 사이에 3초를 쉰다는 뜻이다(일시적 한도 초과·순간 장애가 그 사이 풀리길 기대). 3번을 다 쓰고도 실패하면 그 아이템은 진짜 에러로 처리되어 워크플로우가 멈춘다(continueOnFail를 켜지 않은 경우).

n8n 동작 개념 노트

아이템(item) 흐름

모든 노드는 "아이템 배열"을 받아 "아이템 배열"을 내보낸다. RSS가 N개를 만들면 이후 노드들이 N개를 각각 처리하고, 필터·중복제거를 지나며 개수가 줄어든다. 노드 사이에서 개수가 달라질 수 있다는 점이 06의 페어링 메모와 직결된다.

실행 순서와 비동기 처리

n8n은 연결선을 따라 노드를 한 번에 하나씩, 순서대로 실행한다. 한 노드는 자기에게 들어온 아이템을 모두 처리해 출력을 다 만든 뒤에야 다음 노드로 넘어간다(분기 갈래도 동시에가 아니라 차례로). 그러면서도 "비동기"인 이유는, HTTP 요청처럼 결과를 기다려야 하는 작업에서 n8n이 Node.js의 async/await로 응답을 기다리는 동안 프로세스를 멈추지 않기 때문이다 — 네트워크 대기 시간에도 이벤트 루프가 다른 일을 처리할 수 있다. 08의 코드가 await prepareBinaryData를 쓰는 것이 그 예다. 한 노드 안에서 여러 아이템을 처리할 때의 동시성·간격은 배칭 옵션이 조절한다.

배칭과 재시도

배칭은 한 노드에 들어온 여러 아이템의 외부 호출을 묶음으로 쪼개 간격을 두고 내보내, API 한도를 넘지 않게 하는 장치다(05·07은 5초 간격). 재시도는 호출이 실패(비정상 상태코드·타임아웃·네트워크/ API 오류)했을 때 정해진 횟수만큼 간격을 두고 다시 거는 장치다(05·07은 3초 간격 3회). 둘 다 "느려도 안정적으로"를 위한 설정이라, 글이 많거나 장애가 잦을수록 간격·횟수를 키운다.

pairedItem — "이게 어느 글에서 왔나"

변환·분기를 거치며 순서가 흐트러져도 원본 아이템과의 연결을 유지하는 장치다. 08은 이를 명시적으로 세팅하고, 06은 index 수동 페어링에 의존한다. 안정적인 매칭이 필요하면 index보다 pairedItem이나 고유키(guid) 매칭이 정석이다.

첨부(attachment) 처리 방식

NocoDB 첨부는 "파일은 스토리지에, 레코드에는 참조만" 구조다. 그래서 11이 바이트를 올려 디스크립터를 받고(① 업로드), 12가 그 디스크립터를 레코드 첨부 필드에 배열로 넣는다(② 연결). 레코드에 이미지가 박히는 게 아니라 이미지로 가는 링크가 박힌다.

IF 노드의 두 출력

IF(v2)는 true / false 두 갈래를 내보낸다. 이 파이프라인은 true만 연결해 "필터"로 쓰지만, false 갈래를 이으면 양쪽을 모두 처리하는 진짜 "분기(Router)"가 된다.

설계 메모 · 개선 여지
1
스케줄 주기 드리프트

시간 간격 방식은 직전 실행 기준으로 다음 실행을 잡기 때문에, 23시간은 실행 시각이 매일 앞당겨진다. 고정 시각이 목적이면 cron(0 9 * * *)이 정확하다.

2
필터의 false 갈래 미사용

걸러진 글이 흔적 없이 멈춘다. "왜 안 걸렸나"를 추적하려면 Filter Topic의 false 갈래를 로그 노드로 연결해 탈락 사유를 남긴다.
